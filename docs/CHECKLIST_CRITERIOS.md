# Checklist de criterios de aceptación SIGVA

| US | Criterio | Estado | Cómo verificarlo | Evidencia |
|---|---|---|---|---|
| US-01.1 | La rama principal del repositorio está protegida: solo admite cambios mediante pull request aprobado por al menos otro integrante. | Requiere intervención humana | Revisar la configuración de protección de rama en GitHub. | `CONTRIBUTING.md` / README; configuración manual de GitHub |
| US-01.2 | Un integrante puede clonar el proyecto y ejecutarlo en un equipo limpio siguiendo únicamente el README. | Cumplido y verificado | Seguir los pasos de instalación y ejecución del README. | `README.md` |
| US-01.3 | El pipeline de integración continua se ejecuta automáticamente en cada pull request y bloquea la integración si falla. | Cumplido y verificado | Ejecutar `npm run ci` o revisar el workflow `ci.yml`. | `.github/workflows/ci.yml`, `npm run ci` |
| US-01.4 | El stack tecnológico elegido está documentado junto con la justificación de cada elección. | Cumplido y verificado | Revisar el bloque de stack del README. | `README.md` |
| US-01.5 | Existe un entorno de demostración accesible por ambas comisiones donde está desplegada la última versión de la rama principal. | Requiere intervención humana | Ejecutar la aplicación en un entorno compartido o servidor de demo con variables configuradas. | `README.md` > Entorno de demostración |
| US-02.1 | El modelo representa todas las entidades del dominio. | Cumplido y verificado | Revisar el schema con aeropuertos, vuelos, salidas, clases, usuarios y compras. | `backend/src/db/index.ts`, `docs/modelo-datos.md` |
| US-02.2 | El modelo distingue el vuelo de la salida. | Cumplido y verificado | Revisar tablas `flights` y `departures` y la documentación del modelo. | `backend/src/db/index.ts`, `docs/modelo-datos.md` |
| US-02.3 | El modelo representa los estados de vuelo, salida y compra. | Cumplido y verificado | Checkear los valores `ACTIVE`, `CANCELLED`, `SCHEDULED` y `CANCELLED` en modelo y registro. | `backend/src/db/index.ts` |
| US-02.4 | Los scripts permiten recrear el esquema completo desde cero y cargar datos de prueba con un único comando. | Cumplido y verificado | Ejecutar `npm --prefix backend run db:reset`. | `backend/src/db/reset.ts` |
| US-02.5 | El diagrama ER y el diccionario de datos están documentados y validados por Análisis y Management. | Requiere intervención humana | Revisar la validación de la comisión en la documentación de modelo. | `docs/modelo-datos.md` |
| US-03.1 | Un usuario registrado puede iniciar sesión con email y contraseña; si alguno falla, se muestra mensaje genérico. | Cumplido y verificado | Ejecutar login correcto e incorrecto. | `backend/src/tests/auth.test.ts` |
| US-03.2 | Las contraseñas quedan con hash y sal. | Cumplido y verificado | Inspeccionar el modelo `users.passwordHash` y la creación del administrador. | `backend/src/db/index.ts` |
| US-03.3 | Existen roles administrador, empleado y pasajero; cada usuario solo ve su menú/rutas. | Cumplido y verificado | Verificar login por rol y control de rutas en backend. | `backend/src/tests/auth.test.ts` |
| US-03.4 | El backend rechaza peticiones sin sesión válida y sin permisos (401/403). | Cumplido y verificado | Ejecutar accesos con tokens inválidos y con roles no autorizados. | `backend/src/tests/auth.test.ts` |
| US-03.5 | El usuario puede cerrar sesión y la sesión expira tras 30 minutos de inactividad. | Cumplido y verificado | Probar logout y verificar la expiración del JWT. | `backend/src/tests/auth.test.ts` |
| US-03.6 | Las pruebas cubren inicio de sesión correcto, incorrecto, acceso permitido y denegado por rol. | Cumplido y verificado | Ejecutar la suite de autenticación. | `backend/src/tests/auth.test.ts` |
| US-06.1 | El administrador puede dar de alta un aeropuerto con IATA, nombre, ciudad y provincia. | Cumplido y verificado | Crear un aeropuerto desde la API. | `backend/src/app.ts` |
| US-06.2 | El sistema rechaza un IATA repetido o con formato inválido e informa el error. | Cumplido y verificado | Enviar IATA inválido o duplicado. | `backend/src/tests/auth.test.ts` / API de aeropuertos |
| US-06.3 | El administrador puede modificar un aeropuerto y desactivarlo; no se permite desactivar uno usado por vuelo activo. | Cumplido y verificado | Actualizar un aeropuerto y probar la restricción de baja lógica. | `backend/src/tests/auth.test.ts` |
| US-06.4 | Los aeropuertos desactivados no se ofrecen al crear o modificar vuelos. | Cumplido y verificado | Crear vuelo con origen/destino inactivo y comprobar error. | `backend/src/tests/flights.test.ts` |
| US-06.5 | Solo los usuarios con rol administrador acceden a esta funcionalidad. | Cumplido y verificado | Probar acceso de empleado y admin. | `backend/src/tests/auth.test.ts` |
| US-07.1 | El administrador puede crear un vuelo completo con campos obligatorios y datos de operación. | Cumplido y verificado | Crear un vuelo válido. | `backend/src/tests/flights.test.ts` |
| US-07.2 | Se validan los campos obligatorios, origen/destino, días, período, capacidad y precios. | Cumplido y verificado | Probar errores de validación por payload incompleto o inválido. | `backend/src/tests/flights.test.ts` |
| US-07.3 | Si la hora de llegada es menor o igual a la de partida, se interpreta con `+1`. | Cumplido y verificado | Crear un vuelo nocturno y verificar `arrivalsNextDay`. | `backend/src/tests/flights.test.ts` |
| US-07.4 | Ante un dato inválido, el vuelo no se guarda y el sistema señala el campo y el motivo. | Cumplido y verificado | Validar respuesta con `errors`. | `backend/src/tests/flights.test.ts` |
| US-07.5 | Al guardar, el vuelo queda Activo y genera las salidas. Caso de ejemplo: lunes y viernes del 01/11/2026 al 30/11/2026 generan 9 salidas. | Cumplido y verificado | Ejecutar la prueba automátic de creación de salidas. | `backend/src/tests/flights.test.ts` |
| US-07.6 | Solo los usuarios con rol administrador acceden a esta funcionalidad. | Cumplido y verificado | Probar acceso con usuario empleado/pasajero. | `backend/src/tests/flights.test.ts` |
| US-08.1 | El administrador puede editar todos los datos de un vuelo activo excepto su número, y el cambio se guarda recién después de confirmación explícita. | Cumplido y verificado | Enviar actualización con `confirmed: true` y validar respuesta. | `backend/src/tests/flights.test.ts` (US-08) |
| US-08.2 | Se aplican las mismas validaciones que en la creación del vuelo. | Cumplido y verificado | Ejecutar una actualización inválida y comprobar errores. | `backend/src/tests/flights.test.ts` |
| US-08.3 | Los cambios afectan solo a las salidas futuras; las ya realizadas no se modifican. | Cumplido y verificado | Actualizar un vuelo con período futuro y revisar `Departure` no modificadas en el pasado. | `backend/src/flights.ts` |
| US-08.4 | El sistema impide reducir la capacidad debajo de los pasajes vendidos en alguna salida futura y señala la salida en conflicto. | Cumplido y verificado | Ejecutar con `economySeats` menor a ventas y verificar `409` + `conflicts`. | `backend/src/tests/flights.test.ts` |
| US-08.5 | Si el cambio de días o período deja sin efecto salidas con ventas, se advierte y pide confirmación; al confirmar, pasan a Cancelada. | Cumplido y verificado | Ejecutar cambio de días/período con ventas y confirmación. | `backend/src/flights.ts` |
| US-08.6 | Cada modificación queda registrada en el historial con fecha, hora, usuario responsable, valor anterior y valor nuevo, y se consulta desde el detalle. | Cumplido y verificado | Revisar `flight.history` en el detalle del vuelo. | `backend/src/flights.ts`, `README.md` |
| US-09.1 | El administrador puede cancelar un vuelo completo o una única salida futura previa confirmación explícita. | Cumplido y verificado | Llamar a `POST /api/flights/:id/cancel` con y sin `confirmed`. | `backend/src/flights.ts` |
| US-09.2 | El mensaje de confirmación informa cuántos pasajes vendidos se ven afectados. | Cumplido y verificado | Revisar la respuesta con `affectedPassengers`. | `backend/src/flights.ts` |
| US-09.3 | Tras la cancelación, el vuelo o la salida se muestran con estado Cancelado y no admiten modificaciones posteriores. | Cumplido y verificado | Probar `flight.status === 'CANCELLED'` y la salida cancelada. | `backend/src/flights.ts` |
| US-09.4 | La cancelación no elimina registros: se conservan datos del vuelo, fecha/hora y usuario responsable. | Cumplido y verificado | Revisar `cancelledAt` y `cancelledByUserId` en `Flight`/`Departure`. | `backend/src/db/index.ts`, `backend/src/flights.ts` |
| US-09.5 | No es posible cancelar salidas cuya fecha ya pasó. | Cumplido y verificado | Ejecutar cancelación de fecha pasada con token válido. | `backend/src/flights.ts` |
| US-09.6 | Solo los usuarios con rol administrador acceden a esta funcionalidad. | Cumplido y verificado | Ejecutar la cancelación con un empleado y comprobar `403`. | `backend/src/auth.ts` |
| US-10.1 | El listado muestra paginado de a 20, número, origen, destino, partida, llegada, días, período y estado. | Cumplido y verificado | Ejecutar el listado desde `/api/flights`. | `backend/src/tests/flights.test.ts` |
| US-10.2 | El listado se puede filtrar por estado, origen y destino, y ordenar por número, ruta u horario de partida. | Cumplido y verificado | Probar filtros y orden en los tests. | `backend/src/tests/flights.test.ts` |
| US-10.3 | El detalle del vuelo muestra datos, capacidades/precios, salidas con vendidos y disponibles, y su historial. | Cumplido y verificado | Consultar `/api/flights/:id`. | `backend/src/tests/flights.test.ts` |
| US-10.4 | Desde el detalle se acceden a Modificar y Cancelar, disponibles solo si el vuelo está activo. | Cumplido y verificado | Revisar `status` activo y responder a la UI/API. | `backend/src/flights.ts`, `README.md` |
| US-10.5 | Con 100 vuelos cargados, el listado responde en menos de 2 segundos. | Cumplido y verificado | Ejecutar la medición de rendimiento del listado. | `backend/src/tests/flights.test.ts` (`performance.now()`) |
